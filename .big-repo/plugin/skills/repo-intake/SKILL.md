# 仓库接管

先阅读 [任务协议](references/task-protocol.md)。

用户明确要求“为本项目启用自动维护与交付”时，按 [接入步骤](references/project-workflow.md) 检查项目、推断验证命令与交付规则，再运行 project_workflow.py init。先用 --dry-run 预览。默认仅保存配置与 core 运行目录，交付终点为本地提交；客户端常驻入口、远端交付与展示需显式选择。保留已有说明和用户工作，不修改全局客户端设置。必要认证复用客户端已有连接，不保存凭据值。
显式启用客户端入口后，普通开发需求和反馈由 maintenance-delivery 处理；未启用时不写入常驻说明。旧配置先确认策略，资源升级与解除接入按接入步骤执行。CI 检查名称从实际平台结果和项目规则确认，不能只因本地没有工作流文件就推断无 CI。初始化的 needs-configuration 项由当前 AI 继续调查和补齐，只有凭据或真正缺失的用户决策才交接。

核实仓库与远端、分支、工作区及任务目标；基准固定为完整提交 SHA。按 SDK、代理技能、模型、应用框架、基础设施、开发工具选择相应检查重点，允许混合类型。
列出真正适用的项目规则、生成文件边界、测试入口、发布方式和外部依赖。不能因为没有 GitHub Actions 就认定没有 CI。
检查是否为镜像或要求邮件、Gerrit 等贡献渠道；GitHub PR 不适用时按项目规则交接渠道选择，不创建无效 PR。
首次接入默认保留已有 README；只有显式选择 full 资源和展示策略时才生成托管展示与离线演示。新仓库使用 create，缺少 README 时建立最小入口，再补齐验证并组织首次提交；只有明确给出仓库标识与可见性要求时创建 GitHub 远端。核实公开性后可用 --public；已有内容保留。后续只同步受影响内容，不扩成无关治理。
确认公开性前按私有仓库处理，不将仓库标识发给公开统计服务。
交付任务记录、验证清单、既有工作处理结果和下一步；基线失败按协议诊断并在范围内修复；必要权限缺失时完成未受阻工作后交接。

选择实现或评审标准时，按需阅读 [研究案例](references/cases.md)，区分来源事实与本插件建议。
