# 开发需求与反馈的自动交付

先阅读 [任务协议](references/task-protocol.md)。本技能由 AI 客户端在当前开发任务中执行，用户无需再次交代维护、提交、推送或创建 PR。

## 读取一次配置，执行本轮任务

检查项目根目录的 `.big-repo/config.json` 与 status。旧配置需要显式策略确认，已停用或有待恢复生命周期时先处理对应状态，不开始新任务或远端交付。存在时阅读 [项目工作流](references/project-workflow.md)，使用项目配置的验证、CI、目标分支和交付终点，不自行扩大操作范围。未配置且用户只要求本轮开发时按单次任务协议执行；用户明确要求“为本项目启用自动交付”时先使用 repo-intake 接入，保留项目现有规则。

- 普通问答、解释、只读审查不创建交付任务；用户“只本地”“不推送”“只交付 PR”等明确限制优先，begin 可缩小交付终点。
- 开发需求或反馈到达后先 status；有未完成任务先恢复。新任务用 begin 保存目标、事件标识和实际允许改动的路径，保留并核对用户已有工作，不并行操作同一工作树。
- 确认本轮完成条件、生成文件边界和必要基线，按项目技术栈完成开发或修复。同步本轮影响的文档与示例，不顺便增加展示组件或全仓治理。
- 在最终提交前同步受影响的功能说明、能力目录、模板索引及展示。仅在项目已选择展示策略时使用 repo_tools.py showcase-sync；核实公开性后才加 --public，范围包含实际展示路径；不在 check 中生成或改写文件。
- 执行实际必要验证，诊断并修复失败；提交前精确检查范围，按项目规范组织提交。提交后用 check 验证最终候选，日志和历史失败自动保存在 Git 元数据中。
- 委派独立 AI 子代理或独立会话审查最终提交，修复阻塞发现并重新验证、复审。用 review 登记真实审查者与完整 head SHA，不把实现者自评冒充独立审查。
- 用 deliver 执行已配置的交付：本地提交、推送并创建 PR，或 CI 成功后锁定 head 自动合并。等待中的 CI 只读观察后继续；CI 或审查反馈回到同一任务修复，不能重复创建 PR、盲目重试不确定写入或绕过平台保护。
- 完成后报告实际改动、验证及提交/PR 结果并结束本轮，等待下一次需求或反馈。无任务时不运行定时巡检；新 Issue/评论只有被客户端带入当前任务后才处理。

发布按项目的 explicit-request 策略执行：用户明确要求具体版本时再使用 release-preparation。本项目的 GitHub Actions 发布脚本服务于插件自身发行，不会自动安装到其他项目。

未使用项目工作流脚本时，按任务协议保存真实任务和证据并核对相同交付门槛。提交署名、签署、AI 披露及项目要求的人工审批按实际规则执行。

选择实现或评审标准时，按需阅读 [研究案例](references/cases.md)，区分来源事实与本插件建议。
